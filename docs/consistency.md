## 集成数据一致性

### 背景

企业应用经过一段时间的发展, 逐渐脱离了单体巨石应用, 演变为一个个独立内聚的应用, 这些应用系统数据相对独立, 可以认为是一个 "孤岛".

消除信息孤岛, 打通应用间的数据, 集成企业应用以及各方应用, 形成一个完整的企业业务系统, 就是集成平台的存在价值.

而企业应用自身的数据一致性问题, 一般由应用自身保证. 但企业应用间集成, 就会涉及到分布式事务, 这就对企业应用的一致性支持有了更高的要求. 

传统集成模式则需要系统双方加入一致性的支持, 一般是同步 TCC. 基于此种方案, 对方系统出现不可用时, 会阻塞企业应用自身业务, 这对一些场景来讲是难以接受的.

而且如此一来, 企业应用难度增加不说, 复杂的企业环境 (如使用不同协议的新老系统) 也会增加应用的维护成本, 而且随着企业应用数量的增加, 此部分研发和维护成本, 是非线性增长的. 因为企业应用的增加, 会导致应用需要考虑到自身以及被集成应用连带影响, 最终导致应用集成难以维护, 出现问题难以排查. 

集成平台的出现可以一定程度解决上述问题, 集成平台可以提供一定的数据一致性支持, 而应用本身, 只需要关心自身数据一致性即可.

为了满足企业集成中, 对于数据一致性的要求, 同时降低应用间的耦合, 集成平台提供基于消息的一致性处理方案.

### 解决方案思路

集成平台使用可靠消息来处理上述场景, 目前集成平台支持 RocketMQ 和 Kafka, 后续将不断扩充支持的种类.

由于消息系统的特性, 基本可以保证消息不丢失, 而且可以保证消息至少被消费一次, 即可能发生重复消费.

所以, 此方案需要企业应用提供 `幂等` 支持, 即保证多次处理一个消息, 不会写入重复的数据.

集成平台支持消费 MQ, 也支持生产 MQ 消息, 可以用来处理双向的集成. 具体视企业应用环境. 

以下列举几种常见方式:

1. 对外暴露 MQ, 由集成平台消费, 做协议/数据转换后, 调用第三方服务, 直至消息确认.
2. 对外暴露 Rest/Soap 等标准接口, 由集成平台生产消息, 第三方服务消费, 直至消息确认.
3. 也可对外暴露 Rest/Soap 等标准接口, 由集成平台生产消息, 并由集成平台自身消费, 集成平台调用第三方服务, 直至消息确认. 此为 1 和 2 的结合. 此种方式优点是服务间更解耦, 由于只是配置两个集成流, 所以不在此处做详细说明.

### 可选解决方案

#### 对外暴露 MQ

此模式可以直接对外暴露 MQ, 业务方可直接通过 MQ client 发送消息, 具体流程如下:

1. 企业应用通过 MQ Client 发送消息, 自身执行完后, 转变为 `可发送` 状态
2. 消息在 MQ 持久化, 发送给集成平台
3. 集成平台消费, 触发集成流, 调用第三方服务
4. 第三方服务执行处理逻辑
5. 如执行成功, 则集成平台发起消息确认, 整个链路完成. 
6. 如执行失败或超时, 会重试执行, 直至执行成功或超过重试次数进入死信队列. 集成平台一样可以监听私信队列, 配置通知人工介入或其他动作.

业务处理执行成功时, 时序图示意如下:

```sequence
触发方服务 -> MQ: 发送消息, 状态为"待确认"
MQ -> MQ: 消息存储成功
MQ -> 触发方服务: ACK 确认
触发方服务 -> 触发方服务: 执行具体业务
触发方服务 -> MQ: 发送执行结果
MQ -> MQ: 根据执行结果变更消息状态\n成功为 "可发送", 失败则删除消息
MQ -> 集成平台: 消息发送
集成平台 -> 集成平台: 做相关处理\n如协议转换, 数据转换
集成平台 -> 处理方服务: 调用处理方
处理方服务 -> 处理方服务: 处理业务逻辑
处理方服务 -> 集成平台: 如果成功则直接返回
集成平台 -> MQ: ACK 确认

```

业务处理执行失败时, 时序图示意如下:

```sequence
触发方服务 -> MQ: 发送消息, 状态为"待确认"
MQ -> MQ: 消息存储成功
MQ -> 触发方服务: ACK 确认
触发方服务 -> 触发方服务: 执行具体业务
触发方服务 -> MQ: 发送执行结果
MQ -> MQ: 根据执行结果变更消息状态\n成功为 "可发送", 失败则删除消息
MQ -> 集成平台: 消息发送
集成平台 -> 集成平台: 做相关处理\n如协议转换, 数据转换
集成平台 -> 处理方服务: 调用处理方
处理方服务 -> 处理方服务: 处理业务逻辑
处理方服务 -> 集成平台: 执行失败或超时
MQ -> MQ: 将该消息加入重试队列
MQ -> 集成平台: 尝试再次发送消息给集成平台
集成平台 -> 处理方服务: 再次调用处理方\n如此往复一定次数
MQ -> MQ: 将超过重试次数的消息加入死信队列
MQ -> 集成平台: 集成平台消费死信队列, 发送消息
集成平台 -> 集成平台: 做通知以人工接入方式处理\n或做其他处理

```

在集成平台中, 配置如下:

1. 一个 MQ 触发器(如 RocketMQ, Kafka), 完成相关 nameServer, topic 等配置
2. (可选) 增加一个 Mapper, 将消息体转换为调用服务的入参, 如入参和消息体一致, 则不需要此节点
3. 配置一个调用具体服务的处理器 (Rest/Soap/Dubbo 等等), 这里以 Rest 为例, 配置相关 Host, path, method 等
4. 配置一个消息确认节点, 完成当前消息的确认

#### 对外暴露 Rest/Soap 接口

如果企业应用无法直接访问 MQ, 则可以通过集成平台对外暴露接口, 由集成平台发送消息, 由处理方式来做消费确认. 

执行成功是, 时序图示意如下:

```sequence
触发方服务 -> 集成平台: 调用集成平台对外暴露的服务\n 如  Rest/Soap 
集成平台 -> 集成平台: 做相关处理\n如协议转换, 数据转换
集成平台 -> MQ: 发送消息, 状态为"待确认"
MQ -> MQ: 消息存储成功
MQ -> 集成平台: ACK 确认
集成平台 -> 触发方服务: 返回成功
MQ -> 处理方服务: 消息发送
处理方服务 -> 处理方服务: 处理业务逻辑
处理方服务 -> MQ: ACK 确认
```

```sequence
触发方服务 -> 集成平台: 调用集成平台对外暴露的服务\n 如  Rest/Soap 
集成平台 -> 集成平台: 做相关处理\n如协议转换, 数据转换
集成平台 -> MQ: 发送消息, 状态为"待确认"
MQ -> MQ: 消息存储成功
MQ -> 集成平台: ACK 确认
集成平台 -> 触发方服务: 返回成功
MQ -> 处理方服务: 消息发送
处理方服务 -> 处理方服务: 处理业务逻辑\n执行失败或超时
MQ -> MQ: 将该消息加入重试队列
MQ -> 处理方服务: 尝试再次发送消息给处理方服务
处理方服务 -> 处理方服务: 再次尝试处理\n如此往复一定次数
MQ -> MQ: 将超过重试次数的消息加入死信队列
MQ -> 集成平台: 集成平台消费死信队列, 发送消息
集成平台 -> 集成平台: 做通知以人工接入方式处理\n或做其他处理

```

集成平台配置如下:

1. 配置 Rest/Soap 触发器, 并配置 Path, Method 等
2. (可选) 增加一个 Mapper, 将调用服务的入参转换为消息体, 如入参和消息体一致, 则不需要此节点
3. 发送消息, 例子使用的是 RocketMQ
